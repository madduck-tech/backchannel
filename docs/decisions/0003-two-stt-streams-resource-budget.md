# ADR 0003: Два STT-потока — распределение экземпляров моделей и бюджет ресурсов

Дата: 2026-09-01
Статус: принято

## Контекст

Спека требует раздельную обработку микрофона и системного звука до STT (§10, §38, Milestone 0 п. 4–5).
Опасение: два локальных STT в realtime плюс локальная LLM на одном ноутбуке.

Факты (2026-09-01):

- Люди говорят по очереди: суммарные секунды речи на двух каналах равны секундам на смешанном потоке.
  На каждом канале свой Silero VAD, тишина не распознаётся. Вычисления не удваиваются.
- transcribe.cpp допускает одну активную сессию (stream или run) на загруженную модель.
- В форке слой транскрипции — порт `Transcriber` с адаптерами `streaming` и `segmented`
  (`frontend/src-tauri/src/audio/transcription/`), в `TranscriptChunk` уже есть поле `speaker`.
- Память: Nemotron 3.5 Q8 = 716 MB на экземпляр; GigaAM v3 Q8 = 261 MB; Gemma 4 E2B ≈ 3.6 GiB, E4B ≈ 5.3 GiB.
- Скорость Nemotron Q8 на Ryzen 7 4750U: CPU 8× realtime, Vulkan 14×.
- Batch-путь форка при отставании >30 с выбрасывает старое аудио; streaming-путь лимита не имеет.
- В форке есть `HardwareProfile` (ядра, тип GPU, объём памяти, performance tier).

## Решение

1. **Streaming-модели**: по одному экземпляру модели на канал (YOU и OTHERS). Память ×2.
2. **Batch-модели** (в т. ч. GigaAM, дефолт для русского по ADR 0002): один экземпляр обслуживает оба канала
   через общую очередь сегментов. Память ×1.
3. **Recommendation engine** (§19) считает бюджет как сумму: резерв ОС + LLM + STT × k + запас,
   где k = 2 для streaming и 1 для batch. Расширяем существующий `HardwareProfile`, не пишем сканер заново.
4. **Минимальная целевая машина MVP**: 8 GB RAM без дискретной GPU. На ней Мастер рекомендует
   GigaAM + Gemma 4 E2B либо облачную LLM. Связка Nemotron ×2 + локальная LLM помечается как «16 GB».
5. **Milestone 0** получает измерение: два канала + локальная LLM на минимальной машине,
   STT не отстаёт от realtime при обработке промпта LLM. Выброс аудио при отставании для копилота отключается.

## Последствия

- Главный ресурсный риск — не память, а CPU-конкуренция STT и локальной LLM в проактивном режиме.
  Смягчения: llama-helper — отдельный процесс, ему понижается приоритет и ограничиваются потоки;
  STT получает приоритет. Проверяется измерением из п. 5, а не проектированием.
